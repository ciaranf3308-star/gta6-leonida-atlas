## v0.29.0 — 2026-11-25

**Released: Make it snappy — tile prefetch, a bigger tile cache, and a faster layer toggle.**

- The user's verdict on v0.28's look was "Yeah looks wise with the map I'm happy now" — and then "Just performance is POXY.. no way we can preload all the layers so it's snappy as hell?" v0.29 is the performance lane, profiled first (390px, DPR 2): cold load settled tiles in ~1.6s and the catalogue in ~1.8s, a full zoom-in fired ~190 tile requests, a layer toggle took ~330–440ms to stable pins, and a two-minute drive loaded ~620 distinct tiles — past a third of the old 1,500-entry service-worker cap, which evicted the oldest tile on every put past it. Deliberately NOT done: preloading all 31,527 tiles (~197 MB) up front — that would thrash his phone. What ships instead is the working set, warmed on idle.
- Tile prefetch / cache warming (src/features/map/tile-prefetch.ts): after first paint, on idle (requestIdleCallback, low-priority fetch, cancelled the moment he starts moving), the app warms the whole low-zoom island (z0–z2, 252 tiles, ~1.5 MB) plus the rings around the current view and the child/parent zooms of the viewport — derived from the tiles Leaflet itself already loaded, never from re-implemented projection math, clamped to the pyramid extents so no 404 is ever prefetched. Skipped on save-data / slow-2g and while the tab is hidden. The service worker caches every prefetch, so the next pan or zoom step reads from cache.
- Service-worker cache: the optional-asset cap is now 6,000 entries (~37 MB at ~6 KB/tile) instead of 1,500, and the per-put full cache.keys() scan is gone — the count is kept in memory and re-counted only after a bulk eviction (oldest 100 first). The old cap was also racy under Leaflet's concurrent tile loads: a 1,600-fetch proof run left 1,599 entries in the cache, not 1,500. The count is now a soft cap; the browser quota is the hard limit.
- Tile layer keepBuffer 1 → 2: a pan by a screenful stays inside tiles Leaflet already holds.
- The 2.8 MB place catalogue is preloaded with the HTML parse (<link rel="preload" as="fetch">, same URL the app fetches) instead of starting after the JS bundle parses and React mounts.
- Layer toggle: the marker rebuild is scheduled on the next animation frame instead of running synchronously inside the tap's React commit, and the hero/cluster grouping step is memoized per (camera, visible layers, highlights, selection) — toggling a layer off and back on at the same camera reuses the groups. The 120-DOM-marker cap and clustering are unchanged.
- Verified: profiled before and after with the same harness (scripts/check-v029-perf.mjs, 390px DPR 2, localhost preview). Cold load: first tile 921ms → 1,185ms (inside the before-run's own 815–1,806ms spread — flat within noise), tiles settled 1,584ms → 1,358ms, catalogue ready 1,777ms → 1,375ms.
